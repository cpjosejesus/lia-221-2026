Parallel histogram: atomics and privatization

The first GPU pattern where any thread may write any output element. This session is about making those updates correct with cuda::atomic_ref, understanding why atomics are slow under contention, and making them fast with privatization at the block and thread level and with thread coarsening.

Based on chapter 9 of Programming Massively Parallel Processors (Hwu, Kirk, El Hajj). Runnable code for every kernel: ec2/histogram (laptop or Google Colab). Navigate with → ← or space; press p to print.

  • A histogram counts how many inputs fall in each bin. The sequential loop is O(N), streams the input and keeps the bins in L1: memory-bound.

Read-modify-write: the lost update

two threads increment bins[x], initially 0

The same race outside computers: two customers see seat 9C free on the seat map, both pick it, both mark it taken; two kiosks hand out the same ticket number. Read, modify, write must be one indivisible unit.

Atomic operations in CUDA C++

#include <cuda/atomic>

template <typename T, cuda::thread_scope Scope>
class cuda::atomic_ref;          // like C++20 std::atomic_ref

// wrap an existing object, then operate on it
cuda::atomic_ref<unsigned int, cuda::thread_scope_device>
    bins_ref(bins[b]);
unsigned int old =
    bins_ref.fetch_add(1, cuda::memory_order_relaxed);

// T fetch_add(T arg, cuda::std::memory_order order);
// returns the value *before* the addition. Also:
// fetch_sub, fetch_min, fetch_max, fetch_and, fetch_or,
// fetch_xor, exchange, compare_exchange_*, load, store

// the older C-style API, still common:
atomicAdd(&bins[b], 1u);        // device scope, relaxed
atomicAdd_block(&bins_s[b], 1u); // block scope
  • An atomic operation performs read, modify and write so that no other atomic on the same location can overlap it. The hardware serializes them, in no particular order.
  • atomic_ref does not own the data: it gives atomic access to an ordinary unsigned int in a plain array. Constructing it costs nothing at run time.
  • Two template parameters: the type T (int, unsigned int, float …) and the scope of threads that must see the operation as atomic.
  • The argument of fetch_add has type T: 1 becomes an unsigned int.
  • Why not cuda::atomic<T>? It makes every access atomic from creation; the bins are also zeroed and read non-atomically, so the chapter uses atomic_ref.

Code: the basic histogram kernel

#include <cuda/atomic>
#define NUM_BINS 256

__global__ void histogram_kernel(unsigned char* image,
    unsigned int* bins, unsigned int width, unsigned int height) {
  unsigned int i = blockIdx.x*blockDim.x + threadIdx.x;
  if (i < width*height) {
    unsigned char b = image[i];
    cuda::atomic_ref<unsigned int, cuda::thread_scope_device>
        bins_ref(bins[b]);
    bins_ref.fetch_add(1, cuda::memory_order_relaxed);
  }
}

// host: bins must start at zero
cudaMemset(bins_d, 0, NUM_BINS*sizeof(unsigned int));
histogram_kernel<<<cdiv(width*height, 256), 256>>>(
    image_d, bins_d, width, height);
  • The sequential loop becomes the usual thread index plus a boundary check: one thread per pixel.
  • ++bins[b] becomes an atomic reference to bins[b] and a fetch_add.
  • Device scope: threads of different blocks update the same bins, so the increments must be atomic across the whole GPU.
  • The returned old value is ignored: the thread only needs the increment to happen.
  • Correct, simple, and slow on real images. The rest of the session explains why and fixes it.

  • The order parameter tells the compiler and the hardware which reorderings of this thread's other memory accesses are allowed around the atomic.
  • The only other access is the load of image[i], and the atomic's address depends on its value: the data dependence already forces (1) before (2).
  • Nobody reads the bins while the kernel runs. Results become visible at the kernel boundary (or after __syncthreads() in the privatized kernels).
  • Stronger orders matter when an atomic signals that other data is ready, as in the single-pass scan of a later chapter. Later chapters also use the returned value, e.g. to claim a slot in an output queue.

Privatization: a private histogram per block

3 blocks of 8 threads, 4 bins (real blocks have up to 1024 threads)

Code: private copies in global memory

__global__ void histogram_kernel(unsigned char* image,
    unsigned int* bins, unsigned int* bins_pool,
    unsigned int width, unsigned int height) {
  unsigned int* bins_priv = &bins_pool[blockIdx.x*NUM_BINS];

  unsigned int i = blockIdx.x*blockDim.x + threadIdx.x;
  if (i < width*height) {
    unsigned char b = image[i];
    cuda::atomic_ref<unsigned int, cuda::thread_scope_block>
        bins_priv_ref(bins_priv[b]);
    bins_priv_ref.fetch_add(1, cuda::memory_order_relaxed);
  }
  __syncthreads();

  for (unsigned int b = threadIdx.x; b < NUM_BINS; b += blockDim.x) {
    if (bins_priv[b] > 0) {
      cuda::atomic_ref<unsigned int, cuda::thread_scope_device>
          bins_ref(bins[b]);
      bins_ref.fetch_add(bins_priv[b], cuda::memory_order_relaxed);
    }
  }
}
  • bins_pool: gridDim.x × NUM_BINS counters, allocated and zeroed by the host. Block k owns the slice starting at k × NUM_BINS.
  • Contention drops by roughly the number of active blocks. The copies are small and hot, so they stay in L2.
  • Block scope for the private copy: only this block touches it, which may allow a faster atomic.
  • __syncthreads(), then each thread commits bins b, b + blockDim.x, …: works for any number of bins. Zero bins are skipped.
  • The commit is device scope, but at most one thread per block hits each public bin.

Where the private copy lives

Code: private copies in shared memory

__global__ void histogram_kernel(unsigned char* image,
    unsigned int* bins, unsigned int width, unsigned int height) {
  __shared__ unsigned int bins_s[NUM_BINS];
  for (unsigned int b = threadIdx.x; b < NUM_BINS; b += blockDim.x)
    bins_s[b] = 0;
  __syncthreads();

  unsigned int i = blockIdx.x*blockDim.x + threadIdx.x;
  if (i < width*height) {
    unsigned char b = image[i];
    cuda::atomic_ref<unsigned int, cuda::thread_scope_block>
        bins_s_ref(bins_s[b]);
    bins_s_ref.fetch_add(1, cuda::memory_order_relaxed);
  }
  __syncthreads();

  for (unsigned int b = threadIdx.x; b < NUM_BINS; b += blockDim.x) {
    if (bins_s[b] > 0) {
      cuda::atomic_ref<unsigned int, cuda::thread_scope_device>
          bins_ref(bins[b]);
      bins_ref.fetch_add(bins_s[b], cuda::memory_order_relaxed);
    }
  }
}
  • The only changes: bins_s is __shared__, so the block zeroes it itself, and needs a first barrier before anyone updates it.
  • Shared memory is on the SM, with a latency of a few cycles: shorter latency → higher atomic throughput.
  • Possible only if NUM_BINS counters fit in shared memory (256 bins: 1 KB).
  • Thread block clusters (Hopper and later): blocks of a cluster can share one copy in distributed shared memory, wait for each other with a cluster barrier and commit once per cluster: room for more bins.

The price of privatization: init and commit per block

  • Every block zeroes NUM_BINS counters and commits up to NUM_BINS atomics, however few pixels it processes.
  • Worth it when blocks run at the same time. Blocks beyond what fits on the GPU run in later waves: their overhead buys nothing.
  • Fix: coarsening, fewer blocks with more pixels per thread (next slide).

Thread coarsening: contiguous or interleaved?

toy warp of 8 threads, COARSE_FACTOR = 4, 8-byte memory segments

Code: coarsening, one line apart

__global__ void histogram_kernel(unsigned char* image,
    unsigned int* bins, unsigned int width, unsigned int height) {
  __shared__ unsigned int bins_s[NUM_BINS];
  // ... zero bins_s, __syncthreads() (as before)

  unsigned int segment = COARSE_FACTOR*blockIdx.x*blockDim.x;
  for (unsigned int c = 0; c < COARSE_FACTOR; ++c) {
    // contiguous: each thread walks its own run of pixels
    // unsigned int i = segment + threadIdx.x*COARSE_FACTOR + c;
    // interleaved: the block sweeps blockDim.x pixels at a time
    unsigned int i = segment + c*blockDim.x + threadIdx.x;  
    if (i < width*height) {
      unsigned char b = image[i];
      cuda::atomic_ref<unsigned int, cuda::thread_scope_block>
          bins_s_ref(bins_s[b]);
      bins_s_ref.fetch_add(1, cuda::memory_order_relaxed);
    }
  }
  __syncthreads();
  // ... commit bins_s to bins (as before)
}
// launch: cdiv(width*height, COARSE_FACTOR*256) blocks of 256
  • Each block owns a segment of COARSE_FACTOR × blockDim.x pixels; the grid shrinks by COARSE_FACTOR.
  • Contiguous is the natural CPU choice: each thread streams its own cache lines, and with few threads per cache the lines stay.
  • On a GPU, a warp's 32 loads then hit 32 different places, and with thousands of threads per SM the lines are evicted before the thread comes back.
  • Interleaved: in every iteration the warp reads 32 consecutive bytes, one coalesced transaction.
  • Refinement: read 4 pixels (one 32-bit word) per thread per iteration to use the full width of the load path.

Thread-level privatization

one block of 4 threads, COARSE_FACTOR = 6, interleaved, 4 bins

Code: thread-level privatization

#define NUM_BINS 4            // few bins: 64 intensities each
__global__ void histogram_kernel(unsigned char* image,
    unsigned int* bins, unsigned int width, unsigned int height) {
  __shared__ unsigned int bins_s[NUM_BINS];
  // ... zero bins_s, __syncthreads() (as before)

  unsigned int bins_t[NUM_BINS] = {};    // private to the thread
  unsigned int segment = COARSE_FACTOR*blockIdx.x*blockDim.x;
  for (unsigned int c = 0; c < COARSE_FACTOR; ++c) {
    unsigned int i = segment + c*blockDim.x + threadIdx.x;
    if (i < width*height) {
      unsigned int bin = image[i] / (256/NUM_BINS);
      #pragma unroll
      for (unsigned int b = 0; b < NUM_BINS; ++b)
        bins_t[b] += (bin == b);            // no atomic at all
    }
  }
  for (unsigned int b = 0; b < NUM_BINS; ++b)   // thread -> block
    if (bins_t[b] > 0) {
      cuda::atomic_ref<unsigned int, cuda::thread_scope_block>
          bins_s_ref(bins_s[b]);
      bins_s_ref.fetch_add(bins_t[b], cuda::memory_order_relaxed);
    }
  __syncthreads();
  // ... commit bins_s to bins (as before)      block -> device
}
  • Nobody else can see bins_t, so a plain += is correct.
  • Atomics on shared memory drop from one per pixel to at most NUM_BINS per thread.
  • Why the odd loop instead of ++bins_t[bin]? Registers cannot be indexed at run time, so such an array usually lands in local memory (off-chip, cached). With the unrolled compare-and-add every index is a constant and bins_t stays in registers.
  • Three levels now: registers → shared (block scope) → global (device scope).

Many bins: keep only the frequent ones

  • A full private copy per thread costs NUM_BINS counters per thread: fine for 4 bins, impossible for 256.
  • Many data sets concentrate on a few values (the sky, a background colour). Keep counters only for those in registers; the rare bins go straight to the shared copy with an atomic.
  • The hot bins must be known in advance (a sample, the previous frame) or tracked on the fly.

Privatize only the most recent bin

the elements one thread processes, in order

The book's thread-level privatization for many bins: each thread privatizes one bin, the most recently accessed one, as a counter bin_r in a register. Identical values in localized areas (a sky, a background) become one atomic per run instead of one per pixel. With interleaved partitioning a thread's consecutive pixels are blockDim.x apart, so runs are shorter than in the image itself, but large uniform regions still produce them. (The previous edition called this aggregation.)

Code: privatizing the most recent bin

__global__ void histogram_kernel(unsigned char* image,
    unsigned int* bins, unsigned int width, unsigned int height) {
  __shared__ unsigned int bins_s[NUM_BINS];
  // ... zero bins_s, __syncthreads() (as before)
  unsigned int segment = COARSE_FACTOR*blockIdx.x*blockDim.x;
  if (segment + threadIdx.x < width*height) {
    unsigned int b = image[segment + threadIdx.x];  // first pixel
    unsigned int bin_r = 1;              // private bin: count of b
    for (unsigned int c = 1; c < COARSE_FACTOR; ++c) {
      unsigned int i = segment + c*blockDim.x + threadIdx.x;
      if (i < width*height) {
        unsigned char bNext = image[i];
        if (bNext == b) {
          ++bin_r;                       // same bin: register only
        } else {                         // flush, then switch bins
          cuda::atomic_ref<unsigned int, cuda::thread_scope_block>
              bins_s_ref(bins_s[b]);
          bins_s_ref.fetch_add(bin_r, cuda::memory_order_relaxed);
          b = bNext;
          bin_r = 1;
        }
      }
    }
    cuda::atomic_ref<unsigned int, cuda::thread_scope_block>
        bins_s_ref(bins_s[b]);           // the last run
    bins_s_ref.fetch_add(bin_r, cuda::memory_order_relaxed);
  }
  __syncthreads();
  // ... commit bins_s to bins (as before)
}
  • The first pixel is loaded before the loop, after a boundary check, and bin_r starts at 1; the loop starts at c = 1.
  • Each new pixel bNext is compared with the private bin: equal, increment the register; different, add the old count to the block's bin with one atomic, then switch.
  • The update is always one element behind, so after the loop one more atomic flushes the last run.
  • More statements and variables: with little similarity between consecutive pixels it can be slower than the previous kernel; with high repetitiveness, much faster.
  • The if can diverge, but with no similarity or heavy similarity all threads take the same path, and reduced contention usually pays for it.

Summary

  • A histogram's output location depends on the data, so the owner-computes rule does not apply: any thread may update any bin (output interference). Plain ++bins[b] loses updates through read-modify-write races.
  • cuda::atomic_ref<T, scope> plus fetch_add(1, memory_order_relaxed) makes each update atomic. The scope says which threads must agree; relaxed is enough because nothing else is ordered by the update.
  • Atomics on one location are serialized: their throughput is about the inverse of twice the memory latency. One per 400 cycles is 2.5 M/s against 32 G elements/s of bandwidth. Skewed data concentrates them. Doing them in the last-level cache helps by an order of magnitude.
  • Privatization gives subsets of threads their own copies: per block in global memory, per block in shared memory, per cluster in distributed shared memory, per thread in registers. Less contention and lower latency, paid for with init and commit.
  • Coarsening reduces the number of private copies to initialize and merge; use interleaved partitioning so warps coalesce. Thread-level privatization goes one level further: a whole copy per thread when there are few bins, or only the most recent bin, which pays off when neighbouring data elements are similar.
