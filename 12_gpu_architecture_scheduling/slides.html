Inside the GPU: compute architecture and scheduling

Session 11 showed how to launch a grid of blocks of threads. This session opens the hardware: where the blocks run, how threads are grouped into warps, why branches can cost time, how the GPU hides memory latency, and what limits how many threads fit at once.

Based on chapter 4 of Programming Massively Parallel Processors (Hwu, Kirk, El Hajj). The diagrams are redrawn and animated: use their Play, Step and Reset buttons. Navigate with → ← or space; press p to print.

From the programming model to the machine

  • CPUs are built to make one thread finish fast (low latency). GPUs are built to finish many threads per second (high throughput).
  • Sessions 10–11: we wrote kernels and chose <<<grid, block>>>. We never asked where those threads physically run.
  • Knowing the hardware explains performance that the code alone cannot: why 256 threads per block can beat 32, why an if can halve speed, why “more threads” hides memory delays.

Thread block scheduling: blocks are assigned to SMs whole

10 blocks of unequal length · 2 SMs · up to 3 resident blocks per SM

What block-by-block assignment guarantees

  • All threads of a block go to the same SM, and they are there at the same time. A block only starts when the SM has room for all of it.
  • That is what lets threads of one block cooperate: they can meet at a barrier (__syncthreads()) and exchange data through fast shared memory inside the SM (chapter 5).
  • Threads in different blocks get no such guarantee: their blocks may run at different times, on different SMs, in any order.
  • The run-time keeps a list of blocks not yet started and hands one out whenever a running block finishes and frees its slot.

Hopper adds one level. Blocks can be grouped into a thread block cluster. The blocks of a cluster are scheduled together on the same GPC, can synchronize with each other through the Cooperative Groups API, and can read each other's shared memory (distributed shared memory).

Barrier synchronization: nobody continues until everyone arrives

6 threads of one block · solid = working · hatched = waiting at __syncthreads() · green = after the barrier

A barrier every thread must reach: the wrong and the right way

__global__ void step(float* x, float* y) {
  int t = threadIdx.x;
  if (t % 2 == 0) {
    x[t] *= 2.0f;
    __syncthreads();      // barrier A
  } else {
    x[t] += 1.0f;
    __syncthreads();      // barrier B
  }
  y[t] = x[t] - x[t ^ 1];
}
__global__ void step(float* x, float* y) {
  int t = threadIdx.x;
  if (t % 2 == 0) {
    x[t] *= 2.0f;
  } else {
    x[t] += 1.0f;
  }
  __syncthreads();        // one barrier, all threads
  y[t] = x[t] - x[t ^ 1];
}

Each __syncthreads() call site is a different barrier. It must be reached by all threads of the block, or by none.

Barrier scope and why it is limited to a block

  • Block: __syncthreads(). Cheap, because the whole block is resident on one SM at once.
  • Cluster (Hopper+): cluster-wide barrier through Cooperative Groups; also waits for distributed-shared-memory operations to complete.
  • Grid: possible through Cooperative Groups, but heavy, and only valid when every block of the grid can be resident at the same time.
  • The set of threads a barrier waits for is called its scope.
  • A barrier only works if every thread in its scope can eventually arrive. If one thread could not run until another thread passed the barrier, they would wait forever.
  • CUDA prevents this inside a block by giving the block all its resources before it starts: every thread of the block is running, so every thread can reach the barrier.
  • Blocks, on the other hand, are not allowed to wait for each other. That freedom is what the next slide is about.

Why the two underscores? __syncthreads() is an intrinsic: it looks like a library call, but the compiler replaces it with a special hardware instruction, with no function call. CUDA marks intrinsics with a leading __; gcc and Clang have intrinsics too (for example for CPU vector instructions).

Code: a barrier in a real kernel

#define BLOCK 256

// Reverses every chunk of BLOCK elements of d in place.
// n must be a multiple of BLOCK. Launch with
//   reverseChunks<<<n / BLOCK, BLOCK>>>(d_d);
__global__ void reverseChunks(int* d) {
  __shared__ int s[BLOCK];          // one copy per block
  int t = threadIdx.x;
  int base = blockIdx.x * BLOCK;

  s[t] = d[base + t];               // 1. write my slot
  __syncthreads();                  // 2. wait for all slots
  d[base + t] = s[BLOCK - 1 - t];   // 3. read another's slot
}
  • Thread t reads the slot that thread 255 − t wrote. Without the barrier it could read before that thread has written: a race, and a wrong result that changes from run to run.
  • The barrier is outside any branch, so every thread of the block reaches it.
  • Blocks never need each other: each one reverses its own chunk, so the grid scales to any GPU.
  • __shared__ memory, the per-block scratchpad, is the topic of session 13.

Waves and the tail effect

blocks in the grid
blocks at once

A wave is a group of blocks running at the same time. Many waves help when blocks have uneven work (the hardware rebalances); with few waves, a half-empty last wave leaves SMs idle. To avoid that tail effect, choose a number of blocks that is a multiple of the blocks that fit at once.

Code: which warp and which lane am I?

__global__ void whoAmI(int* warpOf, int* laneOf) {
  // linear index inside the block (row-major)
  int t = threadIdx.y * blockDim.x + threadIdx.x;
  int warp = t / warpSize;   // warpSize is 32 so far
  int lane = t % warpSize;   // position inside the warp

  // one output slot per thread of the grid
  int g = blockIdx.x * (blockDim.x * blockDim.y) + t;
  warpOf[g] = warp;
  laneOf[g] = lane;
}

Why warps? From the von Neumann model to SIMD

SIMD, SIMT and Flynn's taxonomy

Flynn classMeaningExample
SISDone instruction stream, one data streama simple scalar core
SIMDone instruction applied to many dataa GPU processing block; CPU vector units
MISDmany instructions on one data streamrare (some fault-tolerant systems)
MIMDindependent instruction streamsa multicore CPU; the many SMs of a GPU
  • Why SIMD hardware: fetch, decode and the instruction cache are paid once and shared by many lanes, so more chip area and power go to arithmetic.
  • SIMT: you write code for one scalar thread; the hardware groups threads into warps and runs each warp on SIMD lanes. On a CPU you must use vector instructions or intrinsics yourself.
  • Warp size is an implementation choice: 32 on every NVIDIA GPU so far. Read it from warpSize instead of hard-coding it.
  • Warp-level primitives (shuffles, votes; chapters 10–12) let the threads of a warp exchange data without shared memory.
  • The price: the threads of a warp should follow the same instructions. When they do not, we get control divergence.

Control divergence: an if inside a warp

Divergence in loops, and why you cannot count on reconvergence

  • A loop whose trip count depends on the thread (n = a[threadIdx.x]) keeps the warp busy until its longest thread finishes; finished lanes sit idle.
  • Rule of thumb: a condition that depends on threadIdx can diverge; one that is the same for the whole warp (blockIdx, a kernel argument) cannot.
  • Up to Pascal the two paths ran one after the other. From Volta on, independent thread scheduling may interleave them, so threads of a warp are not guaranteed to be back together after a branch.
  • If all threads of a warp must finish a phase before any continues, say so: __syncwarp().

Code: divergent and warp-uniform branches

__global__ void branches(float* x, int n) {
  int t = threadIdx.x;
  int i = blockIdx.x * blockDim.x + t;
  // C: diverges only in the warp that holds i == n
  if (i >= n) return;

  // A: odd and even lanes split in EVERY warp: 2 passes
  if (t % 2 == 0) x[i] = x[i] * 2.0f;
  else            x[i] = x[i] + 1.0f;

  // B: same for all 32 lanes of a warp: 1 pass
  if ((t / warpSize) % 2 == 0) x[i] = x[i] * 2.0f;
  else                         x[i] = x[i] + 1.0f;

  // D: A's work as data, not control flow
  float twice = x[i] * 2.0f, plus = x[i] + 1.0f;
  x[i] = (t % 2 == 0) ? twice : plus;
}
  • A and B do the same amount of work per thread; A costs two passes per warp, B one.
  • If the mapping of work to threads is yours to choose, give each warp a single kind of work (B).
  • C: the early return for the boundary check diverges in at most one warp.
  • D: for very short branches, computing both results and selecting one avoids the branch. The compiler often does this by itself (predication).
  • Never place __syncthreads() after an early return that only some threads take.

Warp scheduling and latency tolerance

each warp: 8 instructions; L = global load, 5 cycles of waiting

An H100 SM has 128 streaming processors but holds up to 2048 threads (64 warps): 16× more threads than it can run in one cycle. Choosing a ready warp every cycle is called fine-grained multithreading. This is why GPUs spend less chip area on caches and branch prediction than CPUs, and more on arithmetic units and memory channels.

Zero-overhead scheduling: switching warps costs nothing

left: a CPU context switch · right: a GPU warp switch

How an SM's resources are partitioned

  • Besides its processors, an SM has thread slots, block slots, registers and shared memory (chapter 5). Every resident block takes its share.
  • The split is dynamic: many small blocks or few large ones. A fixed split would waste slots on small blocks and reject large ones.
  • Occupancy = warps assigned to the SM ÷ the maximum it supports. High occupancy means many warps to switch between, so better latency hiding.
  • Any resource can be the limit. On an H100, full occupancy needs ≤ 32 registers per thread: 65,536 registers ÷ 2048 threads.
  • Shared memory is limited the same way; chapter 5 does that analysis.

Code: let the runtime compute occupancy

__global__ void myKernel(float* x, int n);

int blockSize = 256, blocksPerSM = 0;
size_t dynShared = 0;              // dynamic shared bytes
cudaOccupancyMaxActiveBlocksPerMultiprocessor(
    &blocksPerSM, myKernel, blockSize, dynShared);

cudaDeviceProp p;
cudaGetDeviceProperties(&p, 0);
float occ = (float)(blocksPerSM * blockSize)
          / p.maxThreadsPerMultiProcessor;
printf("%d blocks/SM, occupancy %.0f %%\n",
       blocksPerSM, 100 * occ);

// Or let CUDA suggest the block size:
int minGrid = 0, best = 0;
cudaOccupancyMaxPotentialBlockSize(&minGrid, &best,
                                   myKernel, 0, 0);
myKernel<<<(n + best - 1) / best, best>>>(x_d, n);

  • minGrid is the smallest grid that fills every SM at that occupancy.
  • Compile with nvcc -Xptxas -v to print the registers and shared memory each kernel uses.
  • High occupancy is a means, not the goal: always measure the running time too.

Summary

  • A GPU is an array of SMs (grouped into GPCs). Blocks are assigned to SMs whole, in any order: threads of a block can share memory and barriers; blocks cannot wait for each other. That is what makes the same code scale from a small to a large GPU.
  • Inside the SM, blocks are cut into warps of 32 consecutive threads (row-major for 2D/3D blocks). A processing block fetches one instruction and runs it for the whole warp: SIMD hardware, programmed as scalar threads (SIMT).
  • Threads of a warp that take different branches cost extra passes (control divergence). Boundary checks are the usual cause; their cost shrinks as the data grows.
  • An SM keeps many more warps than it can execute and switches between them for free, so memory latency is hidden by other warps' work.
  • Occupancy = resident warps / maximum warps. Threads, block slots and registers are partitioned dynamically; any of them can be the limit.
