C++ concurrency · session 14

Performance considerations

Sessions 12 and 13 covered how the GPU runs threads and which memories it offers. This session is about the interaction between a kernel's demands and the hardware's limits: how DRAM really works, how to coalesce accesses, hide memory latency, avoid shared memory bank conflicts, and when to coarsen, unroll or double-buffer. It ends with a checklist and a strategy for optimizing any kernel.

Based on chapter 6 of Programming Massively Parallel Processors (Hwu, Kirk, El Hajj). Diagrams are animated or interactive: use Play, Step and Reset, or type your own numbers. Navigate with → ← or space; press p to print.

Demands versus constraints

  • A kernel's speed depends on how its resource demands meet the hardware's resource constraints.
  • The constraint that dominates is the bottleneck. Different kernels, and the same kernel on different GPUs, have different bottlenecks.
  • Most optimizations trade one resource for another. That helps only if the relieved resource was the bottleneck and the one used more does not become a new one.
  • Without this understanding, tuning is guesswork.

Why is DRAM so slow?

one DRAM cell array: decoder, horizontal lines, vertical lines, sense amplifiers

DRAM delivers bursts, caches deliver lines

toy burst of 8 locations

Each access also reads the consecutive locations around it, in parallel, and sends them together: a DRAM burst. The on-chip L1 and L2 caches (SRAM) move data in cache lines for the same reason. Using every byte of a burst or a line is far faster than touching scattered locations.

Coalescing: one request for a whole warp

simplified: memory moved in aligned 128-byte segments (32 floats)

When does the hardware coalesce?

  • All threads of a warp execute the same load instruction at the same time.
  • The hardware checks whether their addresses are consecutive: thread 0 reads X, thread 1 reads X + 1, thread 2 reads X + 2, …
  • If they fall in the same burst or cache line, it combines them into one request for consecutive locations.
  • Alignment matters too: if the first address is not at the start of a burst or line, the same 32 values span one more transfer.
  • Coalescing and tiling work together: tiling cuts how much data goes through global memory, coalescing makes each transfer efficient.

Stores count too. An uncoalesced store can cost more than an uncoalesced load: a partial write may force a read-modify-write of the whole unit, which uses even more bandwidth on GPUs with error-correcting code (ECC) memory.

Row-major layout, again

a 2D array in C and CUDA is one linear array

The matrix product's loop: coalesced or not?

4 consecutive threads, iterations k = 0 … 3

Code: the same loop, two layouts

unsigned row = blockIdx.y * blockDim.y + threadIdx.y;
unsigned col = blockIdx.x * blockDim.x + threadIdx.x;
if (row < Width && col < Width) {
  float Pvalue = 0.0f;
  for (unsigned k = 0; k < Width; ++k)
    // N row-major: N[k][col]
    Pvalue += M[row*Width + k] * N[k*Width + col];
  P[row*Width + col] = Pvalue;
}

// N stored column-major (for example, the transpose
// of a row-major matrix): N[k][col] is at col*Width + k
    Pvalue += M[row*Width + k] * N[col*Width + k];
  • Read the index from the warp's point of view: which parts are the same for all its threads, and which part changes with threadIdx.x?
  • k*Width + col: only col changes, by 1 per thread → consecutive addresses, coalesced. All our kernels so far were coalesced this way.
  • col*Width + k: consecutive threads are Width elements apart → one transfer per thread.
  • The access to M (row*Width + k) is the same address for threads with the same row: one value broadcast, not a problem.
  • Fixes: remap threads to data, change the data layout, or load coalesced into shared memory and do the awkward access there.

Corner turning: load a column of a column-major tile

toy 4 × 4 tile; one load instruction of 4 consecutive threads per step

Code: corner turning in the tiled kernel

// M row-major, N column-major: N[r][c] is at c*Width + r
__shared__ float Mds[TILE][TILE];
__shared__ float Nds[TILE][TILE];
int tx = threadIdx.x, ty = threadIdx.y;
int Row = blockIdx.y*TILE + ty, Col = blockIdx.x*TILE + tx;
float Pvalue = 0;
for (int ph = 0; ph < Width/TILE; ++ph) {
  // M: consecutive tx read consecutive elements of a row
  Mds[ty][tx] = M[Row*Width + ph*TILE + tx];
  // N, naive: N[ph*TILE+ty][Col] → stride Width, slow
  //   Nds[ty][tx] = N[Col*Width + ph*TILE + ty];
  // N, corner turning: tx walks down a column
  int c = blockIdx.x*TILE + ty, r = ph*TILE + tx;
  Nds[tx][ty] = N[c*Width + r];      // coalesced load
  __syncthreads();
  for (int k = 0; k < TILE; ++k)
    Pvalue += Mds[ty][k] * Nds[k][tx];
  __syncthreads();
}
P[Row*Width + Col] = Pvalue;
  • The thread at (ty, tx) now loads element (row ph*TILE + tx, column bx*TILE + ty): the roles of threadIdx.x and threadIdx.y are swapped in the load.
  • Its address c*Width + r changes by 1 with tx: the warp reads 32 consecutive elements of one column. Coalesced.
  • It stores into Nds[tx][ty], so the tile in shared memory has the usual orientation and the inner loop is unchanged.
  • Shared memory is SRAM: it needs no coalescing. But the store Nds[tx][ty] is strided, which causes bank conflicts (slide ).

Coalescing is carpooling

data = commuters, DRAM requests = vehicles

CPUs know bursts too: a CPU cache line maps to part of, one, or several DRAM bursts. Code that uses every byte of each line it touches runs much faster than code that jumps around (code example later in this session).

Hiding memory latency: channels and banks

4 channels × 4 banks; real systems: 1–8 channels, many banks each

How many buses does a processor need?

bus width (bits)
clock (GHz)
needed (GB/s)
  • A bus's bandwidth = width in bytes × 2 (double data rate: a transfer on the rising and on the falling edge) × clock.
  • A modern CPU may need at least 200 GB/s (about 4 DDR5 buses), a GPU more than 1000 GB/s (about 20).
  • Driving that many wires across a circuit board costs too much power. High Bandwidth Memory (HBM) packages the DRAM next to the processor, with shorter, faster and more numerous buses.

Banks overlap the latency

Interleaved data distribution

toy system: 4 channels, 2 banks each, bursts of 2 elements

Parallel threads, parallel DRAM

4 × 4 tiled product, 2 × 2 blocks and tiles, distribution of the previous slide

The relation goes both ways: using DRAM's bandwidth needs many threads accessing memory at once, and the threads' speed needs those accesses spread over channels and banks. If all simultaneous accesses hit the same channel, throughput drops sharply.

Vector loads and stores

z = x + y on 16 elements

Code: vector addition with float4

__global__ void vecAdd4(const float* x, const float* y,
                        float* z, int N) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;  // chunk
  int n4 = N / 4;                    // whole chunks of 4
  if (i < n4) {
    float4 a = reinterpret_cast<const float4*>(x)[i];
    float4 b = reinterpret_cast<const float4*>(y)[i];
    float4 c;                         // one 16 B load each
    c.x = a.x + b.x;  c.y = a.y + b.y;
    c.z = a.z + b.z;  c.w = a.w + b.w;
    reinterpret_cast<float4*>(z)[i] = c;  // one 16 B store
  }
  if (i == n4)                        // one thread: the tail
    for (int j = 4 * n4; j < N; ++j) z[j] = x[j] + y[j];
}

// host: one thread per chunk, plus one for the tail
int threads = N / 4 + 1;
vecAdd4<<<(threads + 255) / 256, 256>>>(x_d, y_d, z_d, N);
  • Casting to float4* makes the compiler emit vector loads and stores of 16 bytes.
  • Two vector loads replace eight scalar ones: 75 % less instruction overhead for the same bytes, and neighbouring threads still read neighbouring chunks (coalesced).
  • Only a quarter as many threads: useful when the kernel cannot run at full occupancy but still needs many bytes in flight.
  • Boundary: when N is not a multiple of 4, the last elements are handled with scalar accesses, and extra threads do nothing.
  • The address of a float4 must be a multiple of 16. cudaMalloc returns aligned memory; an offset like x + 1 would not be.

Shared memory banks

32 banks of 4 bytes, consecutive words in consecutive banks

Shared memory is SRAM with a latency of a few cycles, so it needs no bursts and its banks are narrow. When threads of a warp hit different banks they are served in parallel; several threads on one bank (different addresses) are a bank conflict and get served one at a time.

Padding removes the conflict of a column access

toy: 8 banks, 8 × 8 tile

Code: padding the corner-turning tile

// 32 x 32 blocks: a warp = 32 consecutive threadIdx.x,
// same threadIdx.y
__shared__ float a[TILE_DIM][TILE_DIM];     // TILE_DIM 32
a[threadIdx.x][threadIdx.y] = ...;
// index = x*32 + y  → bank y for every thread:
// a 32-way conflict, 32 passes

__shared__ float a[TILE_DIM][TILE_DIM + 1]; // one extra column
a[threadIdx.x][threadIdx.y] = ...;
// index = x*33 + y  → bank (x + y) % 32: all different
  • The padding column is never used: it only shifts each row by one bank.
  • Cost 1: more shared memory (here 32 more floats per tile), which can matter for occupancy.
  • Cost 2: index arithmetic. i*32 is a shift (i << 5); i*33 needs (i << 5) + i.
  • The benefit depends on the original stride: with 16 columns the warp would hit 2 banks (16-way conflicts), so padding gains less.
  • The other fix is to remap threads to data so that a warp walks along a row.

Thread coarsening

Finest granularity (one output per thread) gives transparent scalability, but parallelizing has an overhead: redundant loads by different blocks, redundant work, synchronization, extra instructions. If the hardware runs everything in parallel the overhead is worth it; if it serializes the threads anyway, the overhead was paid for nothing.

Code: a coarsening loop

// one unit of work per thread
unsigned i = blockIdx.x * blockDim.x + threadIdx.x;
foo(i);

// coarsening factor 4: four consecutive units per thread
unsigned iStart = 4 * (blockIdx.x * blockDim.x + threadIdx.x);
for (unsigned c = 0; c < 4; ++c) {   // the coarsening loop
  unsigned i = iStart + c;
  foo(i);
}
// launch a quarter as many threads
  • Thread 0 handles units 0–3, thread 1 units 4–7, and so on. The number of units per thread is the coarsening factor.
  • The float4 vector addition is coarsening: one thread adds four pairs to use vector loads.
  • The tiled matrix product is another candidate: every block reloads the same input tiles, so fewer blocks with larger output tiles load each input tile fewer times (developed in later chapters).
  • Coarsening matters when it removes real overhead. Fully independent computations gain little from it.

How much coarsening? Count the waves

blocks
blocks at once
coarsening factor
  • Pitfall 1: coarsening where there is no overhead to remove.
  • Pitfall 2: too much coarsening leaves the GPU partly empty, or creates a partial last wave (tail effect). The best factor depends on the device and the data: scalability is less transparent.
  • Pitfall 3: more work per thread can need more registers or shared memory, lowering occupancy.

Loop unrolling

GPUs are throughput-oriented: they tolerate latency mainly through occupancy (many warps). Unrolling is a second tool inside one thread: fewer branch instructions (GPUs have no sophisticated branch prediction, so a branch stalls the thread) and more independent instructions to fill the waits.

Code: unrolling and coarsening loops

// ask the compiler for a factor of 4 (1 = do not unroll)
#pragma unroll 4
for (unsigned i = 0; i < 16; ++i) {
  A(i);
  B(i);
}

// coarsening: each thread handles 4 values of x
int x[4];
for (unsigned c = 0; c < 4; ++c)
  foo(x[c]);          // x[c]: index known only at run time
                      // → x lives in local memory (DRAM)

// fully unrolled (the compiler does it: small constant bound)
foo(x[0]);  foo(x[1]);  foo(x[2]);  foo(x[3]);
// constant indices → x can be promoted to registers
  • The compiler unrolls and schedules aggressively by itself, especially loops with small constant bounds. #pragma unroll N lets the programmer choose.
  • Coarsening loops are the typical case: small and constant, so they unroll completely.
  • Unrolling turns x[c] into x[0] … x[3]: constant indices, so the local array moves from memory to registers (session 13, local memory).
  • So unrolling also enables constant propagation and register promotion: it is what makes coarsening efficient.

Double buffering

4 threads of different speed, 3 iterations

Code: double buffering

// one buffer: two barriers per iteration
for (unsigned i = 0; i < N; ++i) {
  float v = buffer[anotherThreadID];
  __syncthreads();        // write-after-read (false dependence)
  buffer[myThreadID] = f(v);
  __syncthreads();        // read-after-write (true dependence)
}

// two buffers that trade places: one barrier
for (unsigned i = 0; i < N; ++i) {
  float v = inBuffer[anotherThreadID];
  outBuffer[myThreadID] = f(v);
  __syncthreads();        // read-after-write only
  swap(inBuffer, outBuffer);   // pointers to shared arrays
}
  • The first barrier only exists because the read and the write use the same location: a false dependence.
  • With separate buffers, a write can never overwrite something another thread is still reading in this iteration.
  • Why is one barrier still enough? A fast thread writes into the old input buffer only in the next iteration, after the barrier, which every thread reaches only after its reads.
  • The cost is a second buffer; one buffer per iteration would waste much more memory.

An optimization strategy

Code: measuring before optimizing

cudaEvent_t start, stop;
cudaEventCreate(&start);  cudaEventCreate(&stop);
cudaEventRecord(start);
vecAdd4<<<grid, block>>>(x_d, y_d, z_d, N);
cudaEventRecord(stop);
cudaEventSynchronize(stop);
float ms = 0;
cudaEventElapsedTime(&ms, start, stop);

double bytes = 3.0 * N * sizeof(float);   // 2 reads + 1 write
double gbps = bytes / (ms * 1e6);
double peak = 3350;                        // H100: 3.35 TB/s
printf("%.3f ms, %.0f GB/s = %.0f %% of peak\n",
       ms, gbps, 100 * gbps / peak);
# where does the time go? (NVIDIA Nsight Compute)
ncu --set full -o report ./vecadd
ncu --import report.ncu-rep --page details
  • Events time the kernel on the GPU itself, without host overhead.
  • Effective bandwidth = bytes the kernel must move / time. Compared with the peak, it is the speed-of-light analysis of session 13.
  • A memory-bound kernel near 90 % of peak bandwidth has little left to gain; one at 20 % probably has a coalescing or occupancy problem.
  • The profiler reports which unit is the bottleneck (memory throughput, issue stalls, occupancy limiters, bank conflicts), so the next optimization is chosen on evidence.

Code: array of structures versus structure of arrays

struct Particle { float x, y, z, m; };       // 16 B

// array of structures (AoS)
__global__ void sumX(const Particle* p, float* out, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) out[i] = p[i].x * 2.0f;  // stride of 16 B
}

// structure of arrays (SoA)
struct Particles { float *x, *y, *z, *m; };
__global__ void sumX(Particles p, float* out, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) out[i] = p.x[i] * 2.0f;  // consecutive
}
  • AoS: thread i reads p[i].x; consecutive threads are 16 bytes apart. A warp touches 512 bytes to use 128: 25 % of the moved bytes are useful.
  • SoA: all x values are contiguous, the warp reads 128 consecutive bytes, 100 % useful.
  • If every field is used by the same thread, AoS can still be fine, especially with vector loads (one float4 per particle).
  • Converting AoS to SoA is one of the layout changes on the checklist.

Summary

  • DRAM is slow per access (tens of ns) and fast in bulk: it delivers bursts of consecutive locations, and caches move lines.
  • Coalescing: when the threads of a warp access consecutive, aligned addresses, their accesses combine into one request. Read each index from the warp's point of view; fix bad patterns by remapping threads, changing the layout, or corner turning through shared memory.
  • DRAM hides its latency with channels and banks, interleaving data across them. Using them needs many simultaneous, well-spread accesses: occupancy again.
  • Vector loads move 16 B per instruction. Bank conflicts serialize shared memory; padding or remapping removes them.
  • Coarsening removes parallelization overhead when the hardware would serialize anyway; unrolling cuts branches and enables scheduling and register promotion; double buffering removes barriers that only guard false dependences.
  • Optimize iteratively: measure, find the bottleneck, relieve it without overloading another resource, and stop near the roofline.
