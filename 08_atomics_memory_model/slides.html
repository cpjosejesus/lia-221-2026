C++ concurrency · session 08

Atomics and the memory model

One number shared by many threads: counters, flags, the newest pointer. When a mutex is too much and a condition variable is the wrong tool.

Navigate with → ← or space. Press p to print all slides.

Where folder 06 left us

  • A mutex makes a whole critical section exclusive. Right when several fields must change together.
  • A condition variable lets a thread sleep until something is true. Right for waiting, not for updating.
  • Most real sharing is one value: a counter, a “ready” flag, the head of a list.
  • For that, a lock is heavy. Atomics are the third tool.

Remember example 31: the lost update

int oldNum = _tmpVehicles;      // READ
sleep_for(1us);                 // gap
_tmpVehicles = oldNum + 1;      // WRITE stale value

// 1000 tasks -> final count 569
  • Two threads read the same old value.
  • Both write old + 1. One increment vanishes.
  • Folder 06 fixed it with a mutex around the pair.
  • Today: fix it with one indivisible operation.

std::atomic<T>: indivisible operations

  • An atomic operation cannot be observed half done, and two atomic operations on the same object never race.
  • Works for any trivially copyable T.
  • Small T (bool, int, pointer, an 8-byte struct): lock-free, a single instruction.
  • Large T: implemented with a hidden lock. is_lock_free() tells you.
std::atomic<int> counter{0};
counter.fetch_add(1);          // or ++counter
int now = counter.load();

example_46: atomic<Position> (8 B) is lock-free, atomic<VehicleSnapshot> (72 B) is not.

The mistake everyone makes once

// b) each call atomic, the PAIR is not
int old = _n.load();
sleep_for(1us);
_n.store(old + 1);
// 1000 tasks -> 725   still wrong

// c) one read-modify-write
_n.fetch_add(1);
// 1000 tasks -> 1000  right
  • Atomicity of one operation is not atomicity of a sequence.
  • Anything of the shape “read, decide, write” needs a single RMW operation.
  • example_43 prints the three totals side by side.

Read-modify-write operations

OperationEffectReturns
fetch_add(n), fetch_sub(n)add / subtractold value
exchange(x)set to xold value
compare_exchange_weak(expected, desired)if value == expected: set to desiredtrue on success; on failure loads current value into expected
compare_exchange_strong(…)same, never fails spuriouslyfor a single attempt, not a loop

Compare-and-swap (CAS) is the universal building block: every lock-free algorithm is a CAS loop.

The CAS loop

// admit at most `capacity` vehicles
bool tryEnter() {
  int cur = _inside.load();
  while (cur < _capacity) {
    if (_inside.compare_exchange_weak(cur, cur + 1))
      return true;   // we got a slot
    // else: cur was refreshed, re-check
  }
  return false;      // full
}
  • Read the current value.
  • Decide, using that value.
  • Write only if nobody changed it meanwhile; otherwise retry with the fresh value.
  • example_44: 20 vehicles, capacity 3, exactly 3 admitted, no mutex.

A mutex made of one atomic: the spinlock

class Spinlock {
  std::atomic_flag f = ATOMIC_FLAG_INIT;
 public:
  void lock()   { while (f.test_and_set(acquire)) {} }
  void unlock() { f.clear(release); }
};
// works with std::lock_guard<Spinlock>
  • test_and_set is an RMW: returns the old value and sets it.
  • Waiting burns CPU instead of sleeping.
  • example_45, 8 threads pushing vehicles: mutex 20 ms, spinlock 68 ms.
  • Wins only for tiny critical sections with little contention. Use it to understand a mutex, not to replace one.

Atomicity is not ordering

  • The compiler and the CPU reorder memory accesses. Within one thread you never notice.
  • Across threads you do: thread B may see the flag ready = true and still read stale fields of the record written before it.
  • Every atomic operation takes a std::memory_order that says what else it orders.
OrderMeaningUse
relaxedatomic, orders nothing elsestatistics counters
release (store)writes before it are visible to a matching acquire“the record is complete”
acquire (load)reads after it see writes before the releaseconsuming the record
seq_cst (default)acquire + release + one global orderwhen in doubt

Publishing a record: release / acquire

VehicleRecord record;          // plain struct
std::atomic<bool> ready{false};

// producer
record.id = 7; record.name = "Vehicle 7";
ready.store(true, std::memory_order_release);

// consumer
while (!ready.load(std::memory_order_acquire)) {}
use(record);                   // guaranteed complete
  • Release on the store, acquire on the load: everything before the store happens-before everything after the load.
  • Same idea a mutex gives you: unlock is a release, lock is an acquire.
  • example_47. Default seq_cst is always correct; weaker orders are optimizations you justify with a measurement.

False sharing: correct and slow

struct Adjacent {                // same cache line
  std::atomic<long> entered, left;
};
struct Padded {                  // own line each
  alignas(64) std::atomic<long> entered;
  alignas(64) std::atomic<long> left;
};
// two threads, 20M increments each
// adjacent: 742 ms   padded: 194 ms
  • Cores move memory in cache lines (64 B, 128 B on Apple Silicon).
  • Two threads writing two different variables in one line make it bounce between cores.
  • No data race. Just 4x slower. example_48.
  • Tool: std::hardware_destructive_interference_size.

A lock-free stack (Treiber)

void push(Vehicle v) {
  Node* n = new Node{v, head.load()};
  while (!head.compare_exchange_weak(n->next, n)) {}
}
bool pop(Vehicle& out) {
  Node* old = head.load();
  while (old &&
         !head.compare_exchange_weak(old, old->next)) {}
  if (!old) return false;
  out = old->vehicle;   // NOT deleting old
  return true;
}
  • Push and pop are CAS loops on the head pointer. No mutex, no blocking.
  • example_49: 4 producers, 4 consumers, 20 000 vehicles, nothing lost.
  • Two famous problems hide in pop. Next slide.

ABA and memory reclamation

  • ABA. Thread 1 reads head = A and pauses. Others pop A, pop B, push A again at the same address. Thread 1’s CAS sees “still A” and succeeds on a stack it no longer understands. Cure: a version counter next to the pointer, or never reusing addresses.
  • Reclamation. You cannot delete a popped node while another thread may still be reading old->next inside its CAS loop. The example leaks on purpose.
  • Real answers: hazard pointers, epoch-based reclamation, garbage collection. Self-study, and the reason lock-free code is rare in application code.

Choosing the tool

SituationTool
Several fields must change togetherstd::mutex + lock_guard (06)
Wait until something is truecondition_variable (07)
One counter, one flag, one pointerstd::atomic, RMW operations
Decide-then-write on one valueCAS loop
Publish a plain record oncerelease store / acquire load
Parallel counters that crawlcheck false sharing first

Default to seq_cst. Default to a mutex. Reach lower only with a profiler in hand.
