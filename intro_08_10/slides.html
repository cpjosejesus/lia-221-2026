Data parallelism: the idea behind all of it

  • When software is slow, the reason is usually too much data: millions of pixels, billions of grid points, thousands of flights, or a fleet of vehicles.
  • Very often the computation on one piece of data does not depend on the computation on another piece.
  • Independent pieces can be computed at the same time. Then execution speed grows with the number of processors you give the problem.
  • Writing data-parallel code means reorganising the computation around the data, so that the independent parts are visible and can be handed out.

The textbook example: colour to grayscale

Every pixel is an (r, g, b) triple. Its grey level is a weighted sum:

L = 0.299·r + 0.587·g + 0.114·b

Pixel O[i] needs only I[i]. A four-megapixel image is four million independent computations.

Our version of the same shape: an ETA for every vehicle, a price for every order, a blur of the traffic-density map.

Data parallelism vs task parallelism

Task parallelism comes from decomposing the program: a vector addition and a matrix product are two tasks; if independent, they run side by side. I/O and data transfers are tasks too.

There are usually a handful of tasks. Session 09.

Data parallelism comes from decomposing the data: the same operation on every element.

There are usually millions of elements, so this is the main source of scalable performance: more hardware, faster program, same code. Session 10, then the GPU.

Both matter. The dispatcher deciding while couriers ride is task parallelism; pricing a million orders is data parallelism.

Session 10 in one slide: data parallelism on the CPU

  • A blur over a traffic-density image, cut into row strips: input shared read-only, output written in disjoint rows, no lock at all.
  • k-means over two million vehicle positions with combiners: each task accumulates privately, results merge once. 3 ms where a shared counter takes 750 ms.
  • Uneven work: static chunks versus an atomic “next chunk” counter.
  • Random numbers: one generator per task, or it is a data race.
  • Every one of these is a GPU kernel waiting to happen.

The destination: heterogeneous computing

  • A modern computer has a host (the CPU) and one or more devices (GPUs), each with its own memory.
  • CUDA C++ is C++ with a few extra keywords and a small runtime library. One source file holds both host code and device code.
  • Any ordinary C++ program is already a CUDA program with host code only. You add device code where the data parallelism is.
  • Device code is written as kernels: functions that run once per thread, on many threads at the same time.

How a CUDA program runs

  • Serial host code runs on the CPU as usual.
  • A kernel call launches a grid: thousands of device threads, all running the same function on different data.
  • When every thread of the grid is done, the host continues. Host and device can also overlap.
  • Device threads are cheap to create and schedule; CPU threads cost thousands of cycles each. That is why a GPU can afford one thread per pixel.

The loop disappears

// CPU: one thread, a loop over the fleet
void etaAll(const float* dist, const float* speed,
            float* eta, int n) {
  for (int i = 0; i < n; ++i)
    eta[i] = dist[i] / speed[i] * 60.0f;
}
// GPU kernel: one thread, ONE element
__global__
void etaKernel(const float* dist, const float* speed,
               float* eta, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n)
    eta[i] = dist[i] / speed[i] * 60.0f;
}

The grid is the loop: each thread is one iteration, and computes its own i from built-in variables. The if guards the last block, which may have more threads than elements.

Grid, blocks, threads

  • A grid is an array of blocks; every block has the same number of threads, up to 1024, ideally a multiple of 32.
  • threadIdx: position inside the block. blockIdx: which block. blockDim: block size.
  • Like a phone number: area code plus local number gives a unique global index.
  • Blocks may run in any order, a few at a time on a small GPU, hundreds on a large one. Same code, different speed.

The host side: three steps around the launch

void etaOnDevice(const float* dist_h, const float* speed_h,
                 float* eta_h, int n) {
  int size = n * sizeof(float);
  float *dist_d, *speed_d, *eta_d;
  // 1. allocate device memory, copy inputs over
  cudaMalloc((void**)&dist_d, size);
  cudaMalloc((void**)&speed_d, size);
  cudaMalloc((void**)&eta_d, size);
  cudaMemcpy(dist_d, dist_h, size, cudaMemcpyHostToDevice);
  cudaMemcpy(speed_d, speed_h, size, cudaMemcpyHostToDevice);
  // 2. launch the grid: ceil(n / 256) blocks of 256 threads
  etaKernel<<<(n + 255) / 256, 256>>>(dist_d, speed_d, eta_d, n);
  // 3. copy the result back, free device memory
  cudaMemcpy(eta_h, eta_d, size, cudaMemcpyDeviceToHost);
  cudaFree(dist_d); cudaFree(speed_d); cudaFree(eta_d);
}
  • cudaMalloc / cudaFree: like malloc / free, but for device global memory. The pointer it gives you must not be dereferenced on the host.
  • cudaMemcpy: destination, source, bytes, direction.
  • Every call returns an error code. Check it; the examples in books skip that for brevity, you should not.
  • Copying back and forth is the expensive part. Real programs keep data on the device between kernels.

Launch configuration and the guard

  • kernel<<<blocks, threadsPerBlock>>>(args): the two numbers between the brackets define the grid.
  • Blocks needed: ceil(n / threadsPerBlock). In integers: (n + t − 1) / t.
  • Example: n = 1000 vehicles, 256 threads per block → 4 blocks → 1024 threads. The first 1000 compute an ETA; the last 24 fail the if (i < n) and do nothing.
  • Without the guard, 24 threads would write past the end of the arrays.

Compilation and what you need

  • nvcc separates the two halves: host code goes to the ordinary C++ compiler and linker; device code becomes PTX, compiled for the actual GPU when the program runs.
  • Build: nvcc -O2 eta.cu -o eta. Same idea as g++ -std=c++17 -pthread, one more stage inside.
  • Hardware: an NVIDIA GPU. Macs cannot run CUDA at all.
  • No GPU at hand: Google Colab’s free tier gives a GPU with nvcc installed, which is how we will run the CUDA session.

Warm-up questions for the CUDA session

  1. Each thread computes one ETA. Which expression gives its element index? threadIdx.x + threadIdx.y · blockIdx.x + threadIdx.x · blockIdx.x*blockDim.x + threadIdx.x · blockIdx.x*threadIdx.x
  2. Each thread computes two adjacent ETAs. Index of its first element?
  3. n = 8000 vehicles, one element per thread, blocks of 1024 threads, as few blocks as possible. How many threads in the grid?
  4. Allocating n floats on the device: what is the second argument of cudaMalloc? And the first?
  5. Copy 3000 bytes from host array a_h to device array a_d: write the call.

Answers

  1. blockIdx.x * blockDim.x + threadIdx.x: block offset plus position in the block.
  2. (blockIdx.x * blockDim.x + threadIdx.x) * 2: the same global index, times two, and the thread also handles index + 1.
  3. ceil(8000 / 1024) = 8 blocks × 1024 = 8192 threads; 192 of them are stopped by the guard.
  4. Second: n * sizeof(float), bytes not elements. First: (void**)&a_d, the address of the pointer, so the function can fill it in.
  5. cudaMemcpy(a_d, a_h, 3000, cudaMemcpyHostToDevice); destination first.
