Memory architecture and data locality

Session 12 showed how the GPU runs threads. This session is about feeding them: why most kernels so far are limited by memory, which memories CUDA gives us, and how tiling with shared memory cuts global memory traffic, on the GPU and on the CPU.

Based on chapter 5 of Programming Massively Parallel Processors (Hwu, Kirk, El Hajj). Diagrams are animated or interactive: use Play, Step and Reset, or type your own numbers. Navigate with → ← or space; press p to print.

Why memory, after compute

  • The kernels we wrote so far reach only a tiny fraction of the GPU's speed.
  • Reason: their data lives in global memory, off-chip DRAM with long latency (hundreds of cycles) and finite bandwidth.
  • Many warps can hide latency (session 12), but when every thread waits for DRAM, the memory paths congest and the SMs sit idle.
  • The fix: keep reused data in on-chip memories (registers, shared memory) so most accesses never reach DRAM.

The memory wall: why our kernels are slow

§5 introduction: long DRAM latency, finite bandwidth, congestion

Two hardware limits: compute and memory bandwidth

  • Peak compute throughput: arithmetic operations per second. H100: 66.9 TFLOPS in single precision.
  • Peak memory bandwidth: bytes per second from a memory. H100 global memory: 3.35 TB/s.
  • Compute-bound kernel: the arithmetic units are busy most of the time. Memory-bound: the cores wait for data.
  • The deciding number is the compute-to-global-memory-access ratio (arithmetic intensity), in FLOP per byte.
threshold = peak FLOPS / peak bandwidth
          = 66.9 TFLOPS / 3.35 TB/s
          ≈ 20.0 FLOP/B   (H100)

C[i] = A[i] + B[i];      // vector addition
// 1 FLOP, 12 B (load A, load B, store C)
// 1 / 12 = 0.083 FLOP/B  ≪ 20  → memory-bound

The peaks are limits, not guarantees: only well-optimized kernels get close to them.

Matrix multiplication: high potential, low reality

In principle (each element loaded once):

work  = N² dot products × 2N = 2N³ FLOP
data  = 3 matrices × N² × 4 B = 12N² B
ratio = 2N³ / 12N² = N/6 FLOP/B
N = 1024  →  ≈ 171 FLOP/B   (≫ 20: compute-bound)

Our kernel from session 11, inner loop:

for (int k = 0; k < Width; ++k)
  Pvalue += M[row*Width + k] * N[k*Width + col];
// 2 loads (8 B) for 2 FLOP  →  0.25 FLOP/B
  • 0.25 FLOP/B < 20: the kernel is memory-bound.
  • Best possible: 3.35 TB/s × 0.25 FLOP/B = 0.84 TFLOPS, about 1.3 % of 66.9 TFLOPS.
  • Against the H100's tensor cores (989 TFLOPS) it is about 0.08 %.
  • Caches help a little in practice, but the real fix is to reduce global memory accesses in the code. That is what tiling does.

Declaring where a variable lives

__constant__ float coeff[64];   // constant memory
__device__   int   negCount;    // global memory

__global__ void kernel(const float* in, float* out,
                       int n) {
  __shared__ float tile[256];   // shared, per block
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  float acc = 0.0f;             // i, acc: registers

  // global → shared
  tile[threadIdx.x] = (i < n) ? in[i] : 0.0f;
  __syncthreads();              // every thread gets here

  int left = threadIdx.x > 0 ? threadIdx.x - 1 : 0;
  acc = coeff[0] * tile[threadIdx.x]
      + coeff[1] * tile[left];
  if (i < n) {
    out[i] = acc;
    if (acc < 0) atomicAdd(&negCount, 1);  // all threads
  }
}

Scope and lifetime in practice

  • Registers: automatic scalars. One private copy per thread, gone when the thread ends. Fastest, but limited (too many cost occupancy, session 12).
  • Local memory: automatic arrays and spilled registers. Private per thread, but stored in global memory: slow. The compiler may keep an array in registers if all indices are constants.
  • Shared memory: __shared__. One copy per block, visible to all its threads, lives as long as the kernel. The tool for cooperation.
  • Constant memory: __constant__, declared outside functions, read-only in kernels, cached; 64 KB in total.
  • Global variables: __device__. Visible to all kernels and kept between launches; use sparingly (they hurt modularity).

Choosing where a variable lives

Tiling: small fast memory, large slow memory

  • Global memory is large but slow; shared memory is small but fast.
  • Strategy: split the data into tiles that fit in shared memory, like covering a big wall with small tiles.
  • The threads of a block load a tile together, then all of them reuse it from shared memory.
  • Requirement: the computation on each tile can be done independently of the others. Not every algorithm can be tiled.

The tiled kernel (Fig. 5.9)

 1  #define TILE_WIDTH 16
 2  __global__ void matrixMulKernel(float* M, float* N,
                                    float* P, int Width) {
 3    __shared__ float Mds[TILE_WIDTH][TILE_WIDTH];
 4    __shared__ float Nds[TILE_WIDTH][TILE_WIDTH];
 5
 6    int bx = blockIdx.x;  int by = blockIdx.y;
 7    int tx = threadIdx.x; int ty = threadIdx.y;
 8
 9    // the P element this thread computes
10    int Row = by * TILE_WIDTH + ty;
11    int Col = bx * TILE_WIDTH + tx;
12
13    float Pvalue = 0;
14    for (int ph = 0; ph < Width / TILE_WIDTH; ++ph) {
15      // load one M tile and one N tile together
16      Mds[ty][tx] = M[Row*Width + ph*TILE_WIDTH + tx];
17      Nds[ty][tx] = N[(ph*TILE_WIDTH + ty)*Width + Col];
18      __syncthreads();
19
20      for (int k = 0; k < TILE_WIDTH; ++k)
21        Pvalue += Mds[ty][k] * Nds[k][tx];
22      __syncthreads();
23    }
24    P[Row * Width + Col] = Pvalue;
25  }
  • 3–4: shared arrays, one copy per block, reused in every phase.
  • 6–11: automatic scalars, so registers; each thread computes P[Row][Col].
  • 14: one iteration per phase: Width / TILE_WIDTH phases. This is strip-mining: a long loop cut into phases.
  • 16–17: each thread loads one M element and one N element.
  • 18: wait until the whole tile is loaded (read-after-write).
  • 20–21: TILE_WIDTH multiply-adds, all from shared memory.
  • 22: wait until everyone has used the tile before it is overwritten (write-after-read).
  • Pvalue stays in a register the whole time: register tiling.
  • Assumes Width is a multiple of TILE_WIDTH; fixed later.

What tiling buys, and what it does not

  • Global loads drop by a factor of TILE_WIDTH. With 32 × 32 tiles: 0.25 → 8 FLOP/B.
  • On an H100: 3.35 TB/s × 8 FLOP/B = 26.8 TFLOPS, against 0.84 without tiling.
  • Still memory-bound (8 < 20): 40 % of the peak. Chapter 15 pushes further; libraries such as cuBLAS and CUTLASS already do.
  • Locality: each phase works on a small subset of the data, so a small fast memory can serve it.
  • Two kinds of dependence between threads: read-after-write (true: the reader needs the data) and write-after-read (false: only the reuse of the same location creates it).
  • Tiling is not only shared memory: Pvalue in a register is register tiling.
  • CPUs tile too (blocking), but rely on the cache implicitly. A GPU SM runs so many threads that they compete for cache, so GPUs keep reused data on chip explicitly in shared memory.

Boundary checks: when Width is not a multiple of the tile

TILE_WIDTH = 2 · walks every block and phase · after Figs. 5.11 and 5.12

The kernel with boundary checks (Fig. 5.13)

float Pvalue = 0;
int phases = (Width + TILE_WIDTH - 1) / TILE_WIDTH;
for (int ph = 0; ph < phases; ++ph) {
  int mCol = ph * TILE_WIDTH + tx;     // column of M
  int nRow = ph * TILE_WIDTH + ty;     // row of N
  // load M only if the element exists, else 0
  if (Row < Width && mCol < Width)
    Mds[ty][tx] = M[Row * Width + mCol];
  else
    Mds[ty][tx] = 0.0f;
  // load N only if the element exists, else 0
  if (nRow < Width && Col < Width)
    Nds[ty][tx] = N[nRow * Width + Col];
  else
    Nds[ty][tx] = 0.0f;
  __syncthreads();

  for (int k = 0; k < TILE_WIDTH; ++k)
    Pvalue += Mds[ty][k] * Nds[k][tx];
  __syncthreads();
}
if (Row < Width && Col < Width)     // a real P element?
  P[Row * Width + Col] = Pvalue;
  • Three different tests: loading M, loading N, storing P. Rule: every memory access needs a check of its own indices.
  • A missing element is loaded as 0.0f: it adds nothing to the dot product.
  • Threads that compute no P element must still load their tile elements and reach both barriers: other threads of the block need those values.
  • The number of phases becomes ceil(Width / TILE_WIDTH).
  • Rectangular matrices: an j × k M times a k × l N gives a j × l P. Replace Width by j, k or l depending on which dimension it measures (exercise).

Code: launching the tiled kernel from the host

void matMul(const float* M_h, const float* N_h,
            float* P_h, int Width) {
  size_t bytes = (size_t)Width * Width * sizeof(float);
  float *M_d, *N_d, *P_d;
  cudaMalloc(&M_d, bytes);
  cudaMalloc(&N_d, bytes);
  cudaMalloc(&P_d, bytes);
  cudaMemcpy(M_d, M_h, bytes, cudaMemcpyHostToDevice);
  cudaMemcpy(N_d, N_h, bytes, cudaMemcpyHostToDevice);

  int g = (Width + TILE_WIDTH - 1) / TILE_WIDTH;
  dim3 block(TILE_WIDTH, TILE_WIDTH);  // 1 thread per P
  dim3 grid(g, g);                     // cover all of P
  matrixMulKernel<<<grid, block>>>(M_d, N_d,
                                     P_d, Width);

  cudaError_t err = cudaGetLastError();  // launch errors
  if (err != cudaSuccess)
    printf("launch failed: %s\n",
           cudaGetErrorString(err));

  // this copy waits for the kernel to finish
  cudaMemcpy(P_h, P_d, bytes, cudaMemcpyDeviceToHost);
  cudaFree(M_d); cudaFree(N_d); cudaFree(P_d);
}
  • The block must be TILE_WIDTH × TILE_WIDTH: each thread loads exactly one element of each tile.
  • The grid is rounded up, so with the boundary-checked kernel any Width works.
  • TILE_WIDTH = 16 → 256 threads and 2 KB of shared memory per block; 32 → 1024 threads and 8 KB.
  • We checked this kernel by emulating its launch on the CPU (every block, phase and barrier) for Width 3 to 1000 and tiles 2 to 32: the results match a plain triple loop, and the global loads drop by exactly TILE_WIDTH when Width is a multiple of it.

H100: up to 228 KB of shared memory, 2048 threads and 32 blocks per SM. Full occupancy allows at most 228 KB / 2048 = 114 B of shared memory per thread. The SM can also trade cache for more shared memory.

Code: shared memory sized at launch time

// one dynamic array, split by hand into Mds and Nds
__global__ void matrixMulKernel(float* M, float* N,
                                float* P, int Width,
                                int tw) {
  extern __shared__ float Mds_Nds[];
  float* Mds = Mds_Nds;            // first tw*tw floats
  float* Nds = Mds_Nds + tw * tw;  // next tw*tw floats
  ...
  Mds[ty * tw + tx] = ...;         // 1D index
}

// host: pick the tile from what the device offers
cudaDeviceProp p;
cudaGetDeviceProperties(&p, 0);
size_t need32 = 2 * 32 * 32 * sizeof(float);  // 8 KB
int tw = (p.sharedMemPerBlock >= need32) ? 32 : 16;
size_t size = 2 * tw * tw * sizeof(float);
int g = (Width + tw - 1) / tw;
dim3 block(tw, tw), grid(g, g);
matrixMulKernel<<<grid, block, size>>>(
    M_d, N_d, P_d, Width, tw);
  • A fixed __shared__ float Mds[TILE_WIDTH][TILE_WIDTH] is set at compile time; changing it means recompiling.
  • extern __shared__ without a size: the size comes from the third launch parameter, in bytes.
  • There is only one such array per kernel, so Mds and Nds are sections of it, indexed in 1D.
  • sharedMemPerBlock tells the host how much a block may use, so the program can adapt to each GPU.

Summary

  • Speed depends on the compute-to-global-memory-access ratio. Below the device threshold (H100: 20 FLOP/B) a kernel is memory-bound; the roofline shows how far it is from the limit.
  • CUDA offers registers (per thread), shared memory (per block), constant memory (read-only, cached) and global memory. The on-chip ones are small but serve data without using DRAM bandwidth.
  • Tiling: threads of a block load a tile into shared memory together, wait at a barrier, and reuse it. Global traffic drops by TILE_WIDTH.
  • Two barriers per phase: read-after-write before using the tile, write-after-read before overwriting it.
  • Boundary checks make the kernel work for any size: every access tests its own indices, missing elements count as 0.
  • Shared memory and registers are limited per SM: using more can lower occupancy. Locality matters on CPUs as well.
