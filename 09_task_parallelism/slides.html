Task parallelism and measuring speedup

Same tools as before: async, futures, a queue. A different question: not “is it safe?” but “is it faster, and by how much?”

Concurrency vs parallelism, again

  • Concurrency (01 to 08): structure a program as tasks that share things safely.
  • Parallelism (09 to 10): make one computation finish sooner on several cores.
  • Nothing new in the toolbox. Everything new in the questions: how to split, how to combine, what to measure.

Fan-out / fan-in

std::vector<std::future<double>> parts;
for (int t = 0; t < nTasks; ++t)          // fan-out
  parts.emplace_back(std::async(std::launch::async,
      [&, b, e] { double s = 0;
                  for (i = b; i < e; ++i) s += trip(fleet[i]);
                  return s; }));            // partial result
double total = 0;
for (auto& p : parts) total += p.get();    // fan-in
  • Each task owns its chunk and its partial sum. Nothing to lock.
  • The join is the barrier.
  • example_50: 400 000 vehicles, 10 cores. Sequential 383 ms, parallel 51 ms.

Speedup: measure, never assume

speedup(n) = T(1) / T(n)   ideal n   efficiency = speedup / n

  • Same data, same machine, -O2, several runs.
  • example_50 gets 7.5x on 10 cores. Why not 10x? Task creation, combining, memory bandwidth, other processes.
  • Report the sequential time next to the parallel time. A speedup without T(1) is a rumour.

Amdahl’s law

speedup(n) = 1 / (f + (1 − f) / n)

f = fraction of the work that is inherently serial (loading, combining).

speedup(∞) = 1 / f

Fork / join: divide and conquer

double sum(fleet, begin, end, cutoff) {
  if (end - begin <= cutoff)        // leaf
    return sequentialSum(begin, end);
  mid = begin + (end - begin) / 2;
  auto left = std::async(async, sum, fleet, begin, mid, cutoff);
  double right = sum(fleet, mid, end, cutoff);   // this thread
  return left.get() + right;        // join
}
  • One half on a new task, the other half on the current thread.
  • The cutoff stops recursion where a task costs more than the work.
  • Shape of every parallel sort, tree walk, reduction.

Choosing the cutoff

cutoff     leaf tasks   time
1 000 000        1      369 ms   sequential
  250 000        4       91 ms
   50 000       20       53 ms
    5 000      200       48 ms   sweet spot
      500     2000       65 ms   overhead wins
  • Too large: too few tasks, cores idle.
  • Too small: thousands of tasks, spawning dominates.
  • Rule of thumb: a few times more leaves than cores, each leaf worth well over a millisecond.
  • example_52 prints the curve. Exercise 9.1 asks you to find it for orders.

Three primitives: map, reduce, scan

PrimitiveDoesParallel becauseExample
mapout[i] = f(in[i])every element independent; each task writes its own range53

scanout[i] = in[0] ⊕ … ⊕ in[i]three phases: local scans, scan of totals, add offsets54

These three are also the shape of GPU kernels. Learn them on the CPU first; the GPU session reuses every one of them.

Parallel map: layout decides safety

out.resize(in.size());       // allocate ONCE, before tasks
for (t ...) tasks.push_back(std::async(async, [&, b, e] {
  for (i = b; i < e; ++i)
    out[i] = eta(in[i]);     // task t owns out[b..e)
}));
  • Disjoint ranges of a pre-sized vector: no lock, no race.
  • push_back from two tasks: the vector grows concurrently, a data race.
  • example_53: 335 ms → 48 ms on 10 tasks.

Parallel reduce needs associativity

id sum      seq 499999500000  par 499999500000  identical
fuel sum    seq 139999.96      par 139999.96      diff −1.8e−7
1000 − fuel seq −138999.96     par 132999.96      WRONG
average     reduce (sum, count) pairs, divide at the end
  • Integer +: associative and exact.
  • Floating +: mathematically associative, numerically not. Last digits move.
  • −: not associative. Parallel result is garbage.
  • Average, variance, min-and-argmin: reduce a small struct instead. example_56.

Parallel scan in three phases

// 1. each task: local scan of its chunk, record chunk total
// 2. sequential: exclusive scan over the chunk totals -> offsets
// 3. each task: add its offset to its chunk

in:      1 2 3 | 4 5 6 | 7 8 9
phase 1: 1 3 6 | 4 9 15| 7 15 24     totals 6, 15, 24
phase 2: offsets 0, 6, 21
phase 3: 1 3 6 | 10 15 21 | 28 36 45
  • Looks inherently serial, is not.
  • Costs about 2x the work of the sequential scan.
  • example_54: 78 ms sequential, 42 ms with 10 tasks. Needs enough cores and data to break even.

Thread pool: workers created once

template <class Fn>
auto submit(Fn fn) -> std::future<decltype(fn())> {
  auto task = std::make_shared<std::packaged_task<R()>>(fn);
  auto result = task->get_future();
  { lock_guard lock(_mutex); _jobs.push([task]{ (*task)(); }); }
  _cond.notify_one();
  return result;
}
// worker: wait(lock, []{ return stopping || !jobs.empty(); })
//         pop under the lock, run the job OUTSIDE it
  • The folder-07 monitor queue, N workers, packaged_task for the result.
  • Shutdown flag inside the predicate, notify_all, join every worker.
  • example_55: 20 000 jobs. One thread each: 243 ms. Pool of 10: 36 ms.
