Stencil computation on the GPU

A stencil looks like a convolution with a sparse filter. But stencils come from differential equations on 3D grids, and that changes which optimizations pay off. This session: where stencils come from, the basic kernel, why shared-memory tiling buys much less than for convolution, and the two fixes, thread coarsening along z and register tiling.

Based on chapter 8 of Programming Massively Parallel Processors (Hwu, Kirk, El Hajj). Runnable code for every kernel: ec2/06_stencil (laptop or Google Colab). Navigate with → ← or space; press p to print.

Same shape as convolution, different problem

  • Both compute each output from the input element at the same position and its neighbours, so both have halo cells and tiles. What you learned in session 15 still applies.
  • But a stencil approximates derivatives: its weights come from the equation being solved, and it is applied sweep after sweep.
  • The neighbourhood is a star along the axes, not a dense box: far fewer FLOP per loaded element, so far less reuse.
  • The grids are usually 3D, where halos are huge and 1024 threads make a tiny tile.
  • Numerical accuracy pushes towards double precision: more bytes per point, more on-chip memory per tile.

Discretization: a function becomes an array

grid points n
  • A structured grid samples sin(x) on 0 ≤ x ≤ π at constant spacing h; the array F stores F[i] = sin(i·h).
  • The central difference gives the derivative at every grid point from its two neighbours.
  • Smaller h: more accurate, but more storage and more work per sweep.

From a finite difference to a stencil

f′(x) = (f(x+h) − f(x−h)) / 2h + O(h²)

The error is proportional to h²: halve the spacing and it drops by 4. On the grid, x = i·h, so

FD[i] = (F[i+1] − F[i−1]) / 2h

Coefficients −1/2h, 0, +1/2h on F[i−1], F[i], F[i+1], the same at every grid point: a 1D 3-point stencil. A second derivative needs

f″(x) ≈ (f(x−h) − 2f(x) + f(x+h)) / h²
  • A stencil is a geometric pattern of weights applied at every point of a structured grid.
  • The order of a stencil is the number of grid points on each side of the centre. Higher-order differences give more accurate derivatives: order 1 is a 3-point stencil, order 2 a 5-point one, order 3 a 7-point one.
  • A PDE in x and y with derivatives along each axis only (no mixed ∂²/∂x∂y terms) uses points along the axes: the 2D 5-point stencil (order 1) or 9-point stencil (order 2).
  • In 3D the order-1 stencil has 7 points: the centre and its six face neighbours. That is the stencil of this whole session.
  • Example, heat equation: u ← u + s·(sum of the 6 neighbours − 6u), so c0 = 1 − 6s and c1…c6 = s.

Sweep after sweep: an iterative solver

// both buffers hold the boundary values
for (int s = 0; s < sweeps; ++s) {
  launch(stencil_kernel, grid, block,
         d_in, d_out, N);
  std::swap(d_in, d_out);  // no copy
}
  • Each sweep reads only the previous sweep's values, so all points of a sweep are independent.
  • Updating in place would be a race: a thread could read a neighbour already updated in this sweep.
  • Swapping pointers costs nothing. Boundary cells are never written, so both buffers keep them.

Code: the basic 3D 7-point kernel

__global__ void stencil_kernel(const float* in, float* out,
                               unsigned int N) {
  unsigned int i = blockIdx.z*blockDim.z + threadIdx.z;
  unsigned int j = blockIdx.y*blockDim.y + threadIdx.y;
  unsigned int k = blockIdx.x*blockDim.x + threadIdx.x;
  if (i >= 1 && i < N - 1 && j >= 1 && j < N - 1 &&
      k >= 1 && k < N - 1) {
    out[i*N*N + j*N + k] = c0*in[i*N*N + j*N + k]
                         + c1*in[i*N*N + j*N + (k - 1)]
                         + c2*in[i*N*N + j*N + (k + 1)]
                         + c3*in[i*N*N + (j - 1)*N + k]
                         + c4*in[i*N*N + (j + 1)*N + k]
                         + c5*in[(i - 1)*N*N + j*N + k]
                         + c6*in[(i + 1)*N*N + j*N + k];
  }
}
  • One thread per grid point, the familiar 3D mapping: i = z (plane), j = y (row), k = x (column).
  • Threads on the boundary do nothing: those cells keep their boundary values. There are no ghost cells to test inside the sum.
  • c0…c6 come from the equation: hard-coded, or in constant memory like the filter of session 15.
  • Per output: 7 multiplications + 6 additions = 13 FLOP, 7 loads, 1 store.
  • Launch: 8 × 8 × 8 blocks, ⌈N/8⌉³ of them.

Where the seven neighbours live, and what they cost

toy grid N = 8, so a plane is 64 floats

Stencils reuse much less than convolutions

dimension
  • Ideal intensity: every input loaded once, every output stored once, 8 B per point. Stencil: (2P − 1)/8. Convolution, counted as in session 15: 2·md/8.
  • A 2D 5-point stencil: 1.125 FLOP/B, half of the 3 × 3 convolution's 2.25. The input tile does not even need its corners.
  • In 3D the gap explodes: loading a point into shared memory pays off far less for a stencil.

Code: shared-memory tiled kernel

#define IN_TILE_DIM 8
#define OUT_TILE_DIM (IN_TILE_DIM - 2)
__global__ void stencil_tiled_kernel(const float* in, float* out, int N) {
  int i = blockIdx.z*OUT_TILE_DIM + threadIdx.z - 1;
  int j = blockIdx.y*OUT_TILE_DIM + threadIdx.y - 1;
  int k = blockIdx.x*OUT_TILE_DIM + threadIdx.x - 1;
  int tz = threadIdx.z, ty = threadIdx.y, tx = threadIdx.x;
  __shared__ float in_s[IN_TILE_DIM][IN_TILE_DIM][IN_TILE_DIM];
  if (i >= 0 && i < N && j >= 0 && j < N && k >= 0 && k < N)
    in_s[tz][ty][tx] = in[i*N*N + j*N + k];
  __syncthreads();
  if (i >= 1 && i < N-1 && j >= 1 && j < N-1 && k >= 1 && k < N-1 &&
      tz >= 1 && tz < IN_TILE_DIM-1 && ty >= 1 && ty < IN_TILE_DIM-1 &&
      tx >= 1 && tx < IN_TILE_DIM-1)
    out[i*N*N + j*N + k] = c0*in_s[tz][ty][tx]
                         + c1*in_s[tz][ty][tx-1] + c2*in_s[tz][ty][tx+1]
                         + c3*in_s[tz][ty-1][tx] + c4*in_s[tz][ty+1][tx]
                         + c5*in_s[tz-1][ty][tx] + c6*in_s[tz+1][ty][tx];
}
// launch: dim3 block(8, 8, 8), grid(cdiv(N, 6), cdiv(N, 6), cdiv(N, 6))
  • The same structure as the tiled convolution: block = input tile, the outer ring only loads.
  • The "− 1" is the order of the stencil: the halo is one point thick.
  • Out-of-grid slots are not loaded, and never read: only interior points compute, and their neighbours are inside the grid.
  • One barrier between loading and computing.

Tiled intensity against tile size

A block loads t³ points and stores (t − 2)³: 13(t − 2)³ / (4t³ + 4(t − 2)³) FLOP/B, which tends to 13/8 = 1.625 as t grows. But one thread per input point means t³ ≤ 1024: t = 10 at most, in practice t = 8 (512 threads), which gives only 0.96 FLOP/B. Shared memory also grows as t³.

3D tiles are mostly halo

tile width t
  • Halo elements are reused less than interior ones, so the larger their share of the tile, the lower the intensity.
  • A 32 × 32 2D tile is 12 % halo. The 3D tile we can afford, 8 × 8 × 8, is 58 % halo: 296 of its 512 points.
  • More than half of the threads of that block only load.

Thread coarsening: march the tile along z

toy column of 4 output planes; counts for a 32 × 32 block

Code: thread coarsening in z

#define IN_TILE_DIM 32
#define OUT_TILE_DIM (IN_TILE_DIM - 2)
__global__ void stencil_coarse_kernel(const float* in, float* out, int N) {
  int iStart = blockIdx.z*OUT_TILE_DIM;
  int j = blockIdx.y*OUT_TILE_DIM + threadIdx.y - 1;
  int k = blockIdx.x*OUT_TILE_DIM + threadIdx.x - 1;
  int ty = threadIdx.y, tx = threadIdx.x;
  __shared__ float inPrev_s[IN_TILE_DIM][IN_TILE_DIM];
  __shared__ float inCurr_s[IN_TILE_DIM][IN_TILE_DIM];
  __shared__ float inNext_s[IN_TILE_DIM][IN_TILE_DIM];
  bool inXY = j >= 0 && j < N && k >= 0 && k < N;
  if (inXY && iStart >= 1) inPrev_s[ty][tx] = in[(iStart-1)*N*N + j*N + k];
  if (inXY && iStart < N)  inCurr_s[ty][tx] = in[iStart*N*N + j*N + k];
  for (int i = iStart; i < iStart + OUT_TILE_DIM; ++i) {
    if (inXY && i + 1 < N) inNext_s[ty][tx] = in[(i+1)*N*N + j*N + k];
    __syncthreads();                        // all three planes ready
    if (i >= 1 && i < N-1 && j >= 1 && j < N-1 && k >= 1 && k < N-1 &&
        ty >= 1 && ty < IN_TILE_DIM-1 && tx >= 1 && tx < IN_TILE_DIM-1)
      out[i*N*N + j*N + k] = c0*inCurr_s[ty][tx]
          + c1*inCurr_s[ty][tx-1] + c2*inCurr_s[ty][tx+1]
          + c3*inCurr_s[ty-1][tx] + c4*inCurr_s[ty+1][tx]
          + c5*inPrev_s[ty][tx]   + c6*inNext_s[ty][tx];
    __syncthreads();                        // nobody still reads inCurr_s
    inPrev_s[ty][tx] = inCurr_s[ty][tx];
    inCurr_s[ty][tx] = inNext_s[ty][tx];
  }
}
  • 2D block of t² threads, t = 32 → 1024 threads; each computes a column of 30 outputs.
  • Only 3 planes on chip: 3·t²·4 B = 12 KB, instead of 128 KB for a 32³ tile.
  • Intensity: 13·30² / (4·32² + 4·30²) = 1.52 FLOP/B per step; 1.47 over a block of 30 planes (the two extra z planes cost a little).
  • Two barriers: the first protects inNext_s, the second stops a fast thread from overwriting inCurr_s while a neighbour still reads it.

Register tiling: who reads what?

toy 8 × 8 plane; numbers for a 32 × 32 block

Code: coarsening plus register tiling

__global__ void stencil_reg_kernel(const float* in, float* out, int N) {
  int iStart = blockIdx.z*OUT_TILE_DIM;
  int j = blockIdx.y*OUT_TILE_DIM + threadIdx.y - 1;
  int k = blockIdx.x*OUT_TILE_DIM + threadIdx.x - 1;
  int ty = threadIdx.y, tx = threadIdx.x;
  float inPrev = 0.0f, inCurr = 0.0f, inNext = 0.0f;     // registers
  __shared__ float inCurr_s[IN_TILE_DIM][IN_TILE_DIM];  // one plane
  bool inXY = j >= 0 && j < N && k >= 0 && k < N;
  if (inXY && iStart >= 1) inPrev = in[(iStart-1)*N*N + j*N + k];
  if (inXY && iStart < N) {
    inCurr = in[iStart*N*N + j*N + k];
    inCurr_s[ty][tx] = inCurr;
  }
  for (int i = iStart; i < iStart + OUT_TILE_DIM; ++i) {
    if (inXY && i + 1 < N) inNext = in[(i+1)*N*N + j*N + k];
    __syncthreads();
    if (i >= 1 && i < N-1 && j >= 1 && j < N-1 && k >= 1 && k < N-1 &&
        ty >= 1 && ty < IN_TILE_DIM-1 && tx >= 1 && tx < IN_TILE_DIM-1)
      out[i*N*N + j*N + k] = c0*inCurr
          + c1*inCurr_s[ty][tx-1] + c2*inCurr_s[ty][tx+1]
          + c3*inCurr_s[ty-1][tx] + c4*inCurr_s[ty+1][tx]
          + c5*inPrev + c6*inNext;
    __syncthreads();
    inPrev = inCurr;
    inCurr = inNext;
    inCurr_s[ty][tx] = inNext;
  }
}
  • inPrev and inNext replace two shared planes; inCurr stays in a register too, with a shared copy for the neighbours.
  • Shared memory: one third, 4 KB. Cost: 3 more registers per thread, 3072 per block.
  • Registers are faster than shared memory, so the kernel runs faster; global traffic, and so intensity, is unchanged.
  • The book's listing ends with = inNext_s;, a typo: there is no such array here, it must be the register inNext.

All four are memory-bound: the ideal 1.625 FLOP/B is far below the H100 ridge of 20. In practice L1 and L2 catch part of the basic kernel's repeated loads, so the measured gap is smaller than these counts. Some texts count only the loads: that doubles the ideal to 3.25 and gives the basic kernel 13/28 = 0.46. This deck and ec2/06_stencil count loads and stores, as the book does.

Summary

  • Stencils approximate derivatives on structured grids: discretize, replace derivatives by finite differences, apply the same weights at every point. The order is the number of points on each side.
  • A sweep updates every interior point from the previous sweep; boundary cells stay fixed; buffers are swapped between sweeps.
  • The 3D 7-point stencil does 13 FLOP per point: ideal 1.625 FLOP/B, basic kernel 0.41.
  • Tiling helps less than for convolution: sparse stars reuse little, 3D tiles are tiny (t = 8 → 0.96 FLOP/B), mostly halo and poorly coalesced.
  • Thread coarsening in z keeps a 2D block of 32 × 32 threads and only 3 planes on chip: 1.52 FLOP/B with 12 KB.
  • Register tiling keeps the z neighbours, used by one thread only, in registers: a third of the shared memory, the same global traffic.
