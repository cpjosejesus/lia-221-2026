Data parallelism, and the road to GPUs

The same operation on every element of something large. The most scalable parallelism there is, and exactly how a GPU works.

Navigate with → ← or space. Press p to print all slides.

Task parallelism vs data parallelism

  • Task parallelism (09): split the work into tasks. Parallelism limited by how many tasks the program has.
  • Data parallelism (10): split the data. The same function on every element, elements independent. Parallelism grows with the data.
  • Images, point clouds, simulations, matrices, log files: all data-parallel.
  • Three primitives carry over unchanged: map, reduce, scan.

Map over a grid: box blur in strips

// every output pixel: mean of a (2r+1)² window of the INPUT
void blurRows(const Image& src, Image& dst, int r,
              int fromRow, int toRow);

rowsPerTask = ceil(h / nTasks);
for (t ...) std::async(blurRows, cref(src), ref(dst),
                       r, t*rowsPerTask, min(h, (t+1)*rowsPerTask));

1 strip 118 ms · 2: 71 · 4: 37 · 10: 20 ms
  • Input shared read-only: no lock, nobody writes it.
  • Output written in disjoint rows: no lock.
  • Strips, not pixels: 2M tasks would cost more than the blur. example_58.

Map + combine: parallel k-means

struct Partial { vector<double> sx, sy; vector<long> n; };

// each task, its own chunk, its OWN Partial
for (i in chunk) { c = nearest(pts[i], centroids);
                   acc.sx[c] += x; acc.sy[c] += y; acc.n[c]++; }
return acc;

// merge: k entries per task, sequential, cheap
// update: centroid[c] = (sx[c]/n[c], sy[c]/n[c])
  • Assignment step is a map. Update step is a reduce.
  • Nobody writes a shared accumulator. Ever.
  • example_59: 2M vehicles, 4 hotspots found in 21 ms on 10 tasks.

Combiners beat shared accumulators

histogram of 30M speeds, 32 bins, 10 tasks

(a) shared vector + mutex per ++      753 ms
(b) shared vector of atomics         1176 ms
(c) private vector per task, merge      3 ms
  • Atomics are not free: ten cores hammering 32 counters in a few cache lines is slower than a mutex.
  • Accumulate privately, merge rarely. 30M synchronized increments become 10 × 32 additions.
  • example_61. This is the “combiner” of CS-206 and the per-block reduction of CUDA.

Load balancing: static vs dynamic

// dynamic: claim the next `grain` elements atomically
std::atomic<size_t> next{0};
while (true) {
  size_t b = next.fetch_add(grain);
  if (b >= n) break;
  process(b, min(n, b + grain));
}

static, 10 tasks         1046 ms
dynamic, grain 1000       183 ms
dynamic, grain 10         154 ms
dynamic, grain 1        (counter becomes the bottleneck)
  • Equal-size chunks assume equal work. Uneven and clustered work leaves nine tasks idle.
  • Whoever is free takes the next chunk. example_60.
  • Grain too big: imbalance. Too small: contention on the counter.

Embarrassingly parallel, with one trap

long insideCircle(long samples, unsigned seed) {
  std::mt19937_64 rng(seed);   // PRIVATE generator
  ...
}
for (t ...) async(insideCircle, total / n, 1000 + t);

1 task 1096 ms · 2: 555 · 4: 307 · 10: 279 ms
  • No shared state at all. One sum at the end. Near-ideal speedup.
  • One std::mt19937 shared by tasks is a data race.
  • Same seed in every task: the same samples n times, n× the work for nothing.
  • example_62.

Memory layout matters as much as cores

  • A row of an image is contiguous. A column is one element every w floats.
  • A task walking a row strip streams through memory. A task walking a column strip misses the cache on every step.
  • Exercise 10.1 asks you to measure both. Expect a large difference for the same number of operations.
  • On a GPU the same idea is called coalesced access, and it decides whether a kernel is fast or ten times slower.

A GPU is not a faster CPU

  • It is a machine for map, reduce and scan over very large data, with a memory copy at each end.
  • Thousands of simple threads, executed in groups that run the same instruction (SIMT). Branching inside a group costs; locks between threads are the exception, not the rule.
  • Everything you did this session, you will do again next session with a different launcher: kernel<<<blocks, threads>>>(…).
  • Practical: you need an NVIDIA GPU; Macs cannot run CUDA. Google Colab’s free tier offers one with the compiler installed.
